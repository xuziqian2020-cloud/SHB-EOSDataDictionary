# EOS 数据字典业务语义准确度 V6 设计

## 1. 背景

当前规范快照为 Revision 11，已经恢复完整物理结构和 EOS 实体范围：

- 物理表：71,953 张。
- 字段：869,344 个。
- EOS 对应实体表：1,287 张。
- 代码实际使用字段：16,039 个。
- 已获得中文名称的代码使用字段：7,600 个。
- 仍需复核的代码使用字段：8,439 个。

Revision 11 解决了实体筛选为空、快照不一致和待生效状态等基础问题，但业务语义仍存在以下风险：

- 中文名称只翻译了字段尾部，丢失 Owner、Source、Target、Creator 等业务角色。
- 英文拆词结果被误当成正式中文名。
- Account 被全局解释成财务，未区分仓储流水账、库存台账和财务流水账。
- EOS 业务 SQL 中大量可靠的中文输出别名没有被解析。
- C1FlexGrid 标题、资源文本默认值、DataMap 和 SQL CASE 中的业务含义没有充分利用。
- 代码目录被直接当成模块，产生“表-类定义”“其他”“仓库帐”等不稳定分类。
- 单次 SQL JOIN 和名称相似关系被展示得过于确定。
- 部分 ANSI 或 GB 编码源码被错误解码，乱码可能进入证据链。

本设计将推断目标从“尽可能填满中文列”调整为“正式名称高可信、参考名称可解释、每个结论可追溯”。

## 2. 目标

### 2.1 核心目标

- 让新人能够明确区分正式中文名、参考译名、冲突和待确认内容。
- 以 1,287 张 EOS 实体表和 16,039 个代码实际使用字段为首要完善范围。
- 结合 EOS 知识库、实体代码、业务 SQL、窗体标题、菜单、业务流程、枚举和关系上下文推断语义。
- 中文表名、中文字段名、枚举值、表关系和模块归属使用同一套可审计证据模型。
- 保护人工确认结果，后续更新源码或快照时不得被自动结果覆盖。
- 保持 71,953 张表的完整物理结构，但不强制翻译无业务意义的备份表、临时表和历史分表。

### 2.2 成功标准

- 正式中文名称在金标准样本上的准确率不低于 99%。
- 人工锁定和人工确认名称零回退。
- 1,287 张 EOS 实体表全部完成业务分类审计。
- 16,039 个代码使用字段全部具有正式名、参考名或明确的未确定原因。
- 正式中文名中不存在纯英文、原字段名复制或“英文词加名称”的伪中文。
- 所有自动结论都能追溯到知识库条目或源码相对路径及行号。
- 本地生效快照、GitHub 规范快照和 manifest 中的 SHA-256 完全一致。

## 3. 非目标

- 不修改只读 EOS 业务源码根目录中的任何文件。
- 不向 EOS 或金蝶数据库执行任何写操作。
- 不为全部 71,953 张物理表强行生成中文名称。
- 不把低可信词典翻译包装成正式业务定义。
- 不用一次性的 AI 输出直接覆盖人工名称或高可信知识库名称。
- 不改变普通维护人员通过 GitHub Issue 提交人工字典修改的协作模型。

## 4. 双层命名模型

### 4.1 正式中文名

正式中文名用于新人默认阅读，必须满足下列任一条件：

1. 人工确认或人工锁定；
2. 数据库注释明确给出；
3. EOS 知识库明确列出对应表或字段；
4. 唯一定位到物理字段的强业务代码证据，且不存在冲突；
5. 两种以上相互独立的中强证据给出相同语义。

同一 SQL 在多个文件中复制不算独立证据。多个规则都来源于同一条字符串，也只算一个证据源。

### 4.2 参考译名

未达到正式名称门槛，但具有合理业务解释时保存为参考译名。可使用：

- 英文单词拆分和缩写词典；
- 实体属性名；
- 表、字段和关联对象的联合语义；
- 源码目录、窗体名称和模块上下文；
- 单处 SQL JOIN；
- 单一、非直接绑定的 UI 标题；
- AI 对已经收集证据的归纳。

参考译名必须显示“参考”状态，不得与正式名称使用相同视觉样式。

### 4.3 冲突和待确认

- 两个同等级强证据含义不一致时，不自动选胜者。
- 保留当前人工或高等级正式名，新的不同结果进入冲突候选。
- 没有正式名时展示最佳参考译名和其他候选数量。
- 完全没有可靠语义时，正式名和参考名都可以为空，但必须记录未确定原因。
- 禁止用“暂无可靠中文名称”占用正式中文名字段。

## 5. 证据等级

### 5.1 S 级：人工证据

- 人工编辑并确认。
- 人工采用候选。
- 人工锁定。

S 级永远优先于自动证据。人工否决的候选保存证据指纹；证据未发生变化时不重复推荐。

### 5.2 A 级：权威直接证据

- 数据库表或字段注释。
- EOS 知识库中精确匹配的表和字段条目。
- 已确认的业务术语表。
- 非生成代码中的明确实体或属性 XML 业务注释。

### 5.3 B 级：直接业务代码证据

- 能唯一定位到物理字段的 SQL 中文别名。
- 能唯一定位到物理字段的 C1FlexGrid Caption。
- GetResourceText 中的中文默认文本。
- DataColumn.Caption。
- 与字段直接绑定的 DataMap。
- 与字段直接绑定的 SQL CASE WHEN。
- 实体字段和业务对象之间的明确赋值关系。
- 菜单、窗体标题与目标表的增删改入口能够唯一闭环。

### 5.4 C 级：上下文和命名证据

- 英文词和缩写拆分。
- 所在目录。
- 表名前缀。
- 单次 JOIN。
- 字段尾部 ID、No、Date、Time、Qty 等通用词。
- AI 根据上下文生成的解释。

C 级只能生成参考译名，不能单独生成正式名称。

## 6. 源码证据采集

### 6.1 扫描范围

扫描 EOS 的 VB.NET、C#、XML 和必要配置文件，继续排除：

- bin、obj、packages、logs、log、backup 和 .git。
- DLL、EXE、PDB 等二进制文件。
- 明确标识为备份、临时导出或历史副本的目录。

表类生成代码只用于表、字段、属性和类型映射。机械复制字段名的注释不作为中文业务证据。

### 6.2 编码识别

读取源码时依次判断：

1. BOM；
2. 严格 UTF-8；
3. GB18030 或系统 ANSI；
4. 无法可靠解码时标记为不可用证据。

含替换字符或典型乱码片段的中文文本不得进入正式名称或参考译名。

### 6.3 SQL 中文别名

解析 VB 字符串拼接和续行后的 SQL，识别：

- 表别名和字段来源；
- Field AS 中文；
- Field 中文；
- 方括号中文别名；
- FROM、JOIN、CTE 和简单子查询；
- INSERT、UPDATE 和 SELECT 中的实际字段使用。

只有简单物理列能反向命名源字段。计算表达式、CASE 结果、聚合结果和拼接结果只解释查询输出列，不反向修改参与计算的源字段。

被注释的 SQL 不参与推断。.Designer.vb 或自动生成报表中的 SQL 中文别名只能作为参考证据，除非被正常业务代码再次证明。

### 6.4 UI 标题

解析：

- grid.Cols("字段").Caption = "中文"；
- grid.Cols("字段").Caption = GetResourceText(..., "中文默认值")；
- DataColumn.Caption；
- 列变量能够回溯到真实字段时的 Caption；
- 表单标题、页签标题和菜单文字。

字段在同一文件中只能映射到一张物理表时，可作为直接字段证据；多表同名字段无法消歧时只保留为参考候选。

### 6.5 数据映射和枚举

解析：

- 命名 Enum；
- 实体属性类型或显式转换与 Enum 的绑定；
- DataMap 键值；
- 与物理字段绑定的 SQL CASE WHEN；
- 能追踪到具体字段值的 Select Case。

普通页面流程控制、按钮状态切换和 SelectedIndex 分支不视为数据库枚举。

## 7. 表名推断

表名按以下顺序处理：

1. 人工名称；
2. 数据库注释；
3. 知识库精确条目；
4. 实体类业务注释；
5. 菜单或窗体与该表 CRUD 的闭环；
6. 基表语义和结构后缀；
7. 命名翻译候选。

Deleted、History、Event、Item、Detail 等后缀只有在基表已确认且结构关系能够证明时，才继承基表语义。

Bak、日期分区、临时表和导入中间表默认归入低价值对象。除非 EOS 实际业务代码仍在使用，否则不进入新人默认范围。

Account 必须结合上下文处理：

- Account_Pallet_FA_Not_IO：非托盘出入库流水账；
- Account_Storage_IO：仓储出入库流水账；
- Account_Storage_Part_Inv：仓储区库存；
- DA_Account：财务流水账。

不得建立 Account 等于财务的全局规则。

## 8. 字段名推断

字段翻译必须保留完整业务角色，不能只翻译最后一个通用词。

示例规则：

- 仓储上下文中的 Owner_Company_ID：货主公司ID；
- DA_Acceptance.Owner_Company_ID：按已确认 EOS 业务口径采用货主公司ID，Company.Company_ID 关联用于验证目标实体；
- Creator：创建人；
- Editor：编辑人；
- Source_XXX_ID：来源XXX ID；
- Target_XXX_ID：目标XXX ID；
- Kis_FSTOCK_NUMBER：根据实际单据上下文翻译为金蝶入库单号等具体含义；
- op_createtime：操作记录创建时间；
- Spec：规格；
- Currency：币别；
- Unit：单位；
- Inv：库存；
- Program：项目；
- Money：金额；
- CompanyID：公司ID；
- Using：使用中或是否启用，最终名称由数据类型和业务代码决定。

布尔字段必须优先使用“是否……”形式，但数据库字段本身表示状态而不是判断时，可以使用“启用状态”“使用状态”等业务名称。

同一缩写在不同模块含义不同时，不进入全局缩写词典，必须建立带模块或表上下文的词义。

## 9. 关系推断

### 9.1 正式关系

满足任一条件：

- 数据库真实外键；
- 实体导航引用、字段映射和 SQL JOIN 中至少两类证据一致；
- 同一字段关系在两个独立生产业务文件中重复出现，并能通过主键或唯一键确定方向。

### 9.2 参考关系

- 只有单处 SQL JOIN；
- 仅名称相似；
- 只有单次字段赋值；
- 关系方向无法通过主键、唯一键或实体结构确认。

### 9.3 排除

- 临时表和表变量；
- 查询结果别名；
- 报表计算列；
- 备份表或日期分表之间的偶然关联；
- 同名字段但没有 JOIN 或实体证据；
- OR 条件、函数转换或复杂表达式导致无法唯一确定的关联。

关系证据需保存父表、子表、双方字段、关系方向、来源文件、行号和可信状态。

## 10. 模块归属

每张业务表同时保存：

- 主业务模块：主要由哪个业务流程维护；
- 使用模块：还有哪些模块读取或引用。

主模块判定顺序：

1. 知识库业务流程和模块索引；
2. 菜单入口与窗体标题；
3. 对该表执行新增、修改、删除的主要业务入口；
4. 各模块生产代码的使用频次；
5. 实体目录、表名前缀和命名参考。

读取频次不能覆盖维护归属。例如基础资料表可能被多个模块读取，但主模块仍由其维护流程决定。

模块名称归一到统一业务分类，消除“表-类定义”“其他”“仓库帐”“仓储”“仓储与库存”等目录型或重复型名称。无法确认时主模块保留待确认，使用模块仍可展示。

## 11. 快照数据模型

### 11.1 正式名称保持兼容

TableMetadata.ChineseName 和 FieldMetadata.ChineseName 继续只保存正式中文名。现有人工优先级、IsManualOverride、IsLocked 和 OriginalAutomaticValue 语义保持不变。

OriginalAutomaticValue 继续用于人工覆盖前的自动值，不复用为参考译名。

### 11.2 新增推断数据

表和字段新增独立的建议模型，至少保存：

- SuggestedChineseName：最佳参考译名及其状态、分数和证据；
- AlternativeChineseNames：发生冲突时的其他候选；
- SuggestionReason：候选成立或未能升级为正式名的原因；
- RejectedSuggestionFingerprints：已人工否决且证据未变化的候选指纹。

表新增 UsedByModules，用于保存使用模块及其证据。ModuleName 继续表示唯一主模块。

采用或修改候选时，继续提交现有 ChineseName 人工修改事件。否决候选需要新增可审计的 SuggestionDecision 元数据事件，至少记录对象稳定键、候选值、证据指纹、决定、维护人和时间。客户端与 GitHub 工作流必须同时支持并校验该事件后，才把“否决候选”描述为可跨用户共享；否则只能作为本机审阅状态。

只为 EOS 实体表、代码实际使用字段、知识库业务表及其可靠关联基础表保存完整候选证据，避免 869,344 个字段全部携带低价值候选造成快照膨胀。

### 11.3 兼容与公开安全

- 本次只增加可选成员，继续使用 SnapshotData.FormatVersion = 1，避免现有 Revision 11 客户端因版本检查而拒绝整个快照。
- 新客户端可以读取旧快照，缺失建议数据时按空值处理。
- 必须使用 Revision 11 发布版客户端验证读取 V6 新快照并安全忽略新增成员。若实测不兼容，则必须改用兼容承载方式或先完成客户端升级，不得伪装成格式 1 直接发布。
- 兼容性测试同时验证“新客户端读取旧快照”“Revision 11 客户端读取新快照”“新格式稳定序列化”和压缩回读。
- GitHub 公开快照中的源码路径转换为仓库相对路径。
- 证据摘要不得包含 Token、密码、服务器地址、本机绝对路径或完整敏感 SQL 参数。
- 公开证据只保留支持结论所需的最短摘要，不发布大段业务源码。
- 新增建议和候选也必须经过现有公开证据清理流程。

## 12. 界面设计

### 12.1 列表

表列表增加“参考译名”，字段列表增加“参考译名”。正式名称存在且与候选一致时，参考列可以为空，减少重复信息。

状态视觉：

- 正式中文名：正常高对比度文字；
- 参考译名：柔和橙色并显示“参考”；
- 冲突：红色状态；
- 待确认：中性灰色；
- 人工确认或锁定：清晰的已确认标识。

不得使用低对比度小字号，也不得把状态、计数和搜索框挤在同一行。

### 12.2 搜索和筛选

搜索始终在当前对象范围内执行，并覆盖：

- 正式中文名；
- 参考译名；
- 英文表名和字段名；
- 实体类；
- 主模块和使用模块；
- 枚举中文值。

新增筛选：

- 仅看正式名称为空；
- 仅看存在参考译名；
- 仅看冲突；
- 仅看代码实际使用字段；
- 仅看人工确认；
- 仅看待确认。

### 12.3 证据审阅

详情页展示：

- 正式名称和参考译名；
- 可信状态和评分；
- 推断理由；
- 来源类型；
- 源码相对路径及行号；
- 命中的 SQL、Caption、枚举、关系或知识库条目；
- 其他候选和未采用原因。

提供“采用候选”“修改并确认”“否决候选”。这些操作继续进入现有本地 outbox 和 GitHub Issue 审计流程。

## 13. 推断流水线

1. 读取当前远程规范快照作为业务基线。
2. 加载 EOS 知识库、术语表和模块分类。
3. 单次流式扫描 EOS 源码，生成规范化证据记录。
4. 按表键和字段键建立索引，禁止对每张表重复扫描全部源码。
5. 解析表名、字段名、枚举、关系和模块候选。
6. 对候选进行独立证据去重、冲突检测和可信等级判定。
7. 合并时优先保护人工和高可信现有值。
8. 生成候选快照和全量审计报告。
9. 执行自动测试、金标准回归、快照验证和公开内容检查。
10. 所有门槛通过后才提升规范修订；失败时保留 Revision 11。

相同输入必须产生相同排序、相同候选、相同公开快照字节和相同 SHA-256。

## 14. 质量验证

### 14.1 金标准

建立版本化金标准，至少包含：

- 200 张表；
- 1,200 个字段；
- 100 条关系；
- 100 组枚举值；
- 采购、仓储、生产、销售、财务、质量、人力资源、物料 BOM、计划和系统配置等主要模块。

金标准优先来自人工确认、数据库注释、知识库精确条目和直接业务代码证据。

金标准同时包含“正确名称”“错误名称”和“证据不足时必须保持待确认”三类样本，避免通过少填正式名称虚增准确率，也避免为了提高覆盖率制造错误结论。

### 14.2 自动测试

实施前先写失败测试，覆盖：

- SQL 有 AS 和无 AS 的中文别名；
- 表别名和同名字段消歧；
- 计算列不污染源字段；
- GetResourceText 中文默认值；
- DataMap 和 SQL CASE 枚举；
- Select Case 流程控制排除；
- Owner_Company_ID 的上下文差异；
- Account 的仓储与财务差异；
- op_createtime 和常见复合字段；
- 单一关系降级和多证据关系升级；
- 主模块与使用模块区分；
- ANSI、GB18030、UTF-8 和乱码拒绝；
- 人工锁定、人工否决和冲突保留；
- 新旧快照兼容、稳定序列化和公开证据清理。

### 14.3 发布硬门槛

## 16. 发布与恢复

- Revision 11 在整个生成和验证阶段保持不变。
- 候选数据库、报告和程序构建输出放入隔离目录。
- 发布前保留当前本地 dictionary.db 和 Revision 11 规范快照备份。
- 远程 HEAD、Revision 或 manifest SHA 在生成期间变化时停止发布并重新基线化。
- 发布时使用远程当前修订号加一，不在设计中硬编码具体 Revision。
- SuggestionDecision 作为格式 1 的可选元数据事件扩展，先发布并验证兼容客户端与 GitHub 工作流，再提升包含新数据的规范快照；如需任何破坏性协议变化，则另行设计并协调版本升级。
- 同一份压缩快照字节同时用于本地安装和 GitHub 规范仓库。
- 推送后重新从远程下载并校验 SHA，再通过正式同步入口安装。
- 任一发布门槛失败时不覆盖当前 Revision 11。
- 已发布后若发现严重语义回归，通过下一规范修订恢复业务值，不删除既有审计历史。
