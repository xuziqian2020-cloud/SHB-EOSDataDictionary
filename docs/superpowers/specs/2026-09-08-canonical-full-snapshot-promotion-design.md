# EOS 数据字典 Revision 11 全量规范快照提升设计

## 1. 目标

以 GitHub 远程 Revision 10 为唯一最新基线，重新结合 EOS 源码与项目知识库生成高可信业务数据字典，将同一份规范快照提升为 Revision 11，并保证：

- 本机与 GitHub 远程使用完全相同的压缩快照字节和 SHA-256。
- 71,953 张物理表及其字段结构完整保留。
- “仅显示 EOS 有对应实体”恢复为真实源码实体集合，目标数量为 1,287。
- Revision 10 已生效的人工维护结果不丢失。
- 本机连接配置、密码、Token、绝对路径和私有环境信息不进入远程仓库。
- 无效且已被后续修改取代的 Issue #2 不再永久显示为“待生效 1”。
- 后续多人维护仍使用 Issue 事件流，保留顺序、幂等和审计能力。

## 2. 已确认现状与根因

### 2.1 远程规范状态

- 远程分支：`main`
- 当前远程提交：`91aa9ddd60bd6fa9b9bb092c861dd670214ec900`
- 当前规范修订：Revision 10
- 当前规范快照 SHA-256：`bbee1132eb8acc772913bddadc795f779ac2dbb7bc75bd4f0c67ba6c2fd44897`
- 当前物理表数量：71,953
- 当前 `EntityName` 数量：0

### 2.2 实体范围为空

主界面只把满足下列条件的表加入 EOS 实体范围：

1. `EntityName` 非空；
2. 可信状态为 `CodeEvidence`；
3. 来源是 `EOS 源码实体类`，或证据规则是 `KisEntityClass` / `TableNameProperty`。

Revision 10 的 `EntityName` 为 0，因此勾选“仅显示 EOS 有对应实体”后结果必然为空。旧本地 V4 快照包含 1,287 个实体映射，但它基于 Revision 8；应用启动同步后，Revision 10 按远程优先规则替换了旧本地共享快照。

### 2.3 永久待生效记录

本机 `PendingDictionaryOperations` 中有一条 `Submitted` 记录对应 Issue #2。该 Issue 被工作流标记为 `dictionary-event-invalid`，从未进入规范事件链，因此旧客户端永远无法把它标记为完成。

Issue #2 的意图是把 `dbo.DA_Account.ModuleName` 从“采购”改为“财务”。远程 Revision 8 已通过后续合法事件把该值从“财务”改为“财务管理”，因此 Issue #2 已被后续结果取代，不能再次应用为“财务”。

## 3. 方案选择

采用“管理员全量规范快照提升”，不把数千条自动推断拆成上百个普通维护 Issue，也不提交原始 `dictionary.db`。

### 3.1 不选择普通 Issue 批量发布

普通 Issue 适合人工维护的少量业务元数据。单个 Issue 最多100项操作；数千条自动推断会形成大量 Issue，增加队列拥堵、人工审阅和失败恢复成本。

### 3.2 不选择原始 SQLite 上传

原始 SQLite 同时承担本机缓存和配置存储，可能包含连接配置、加密凭据、本机目录及本地界面状态，不能作为公开共享制品。

### 3.3 管理员提升的适用边界

全量提升仅用于这次“远程基线整体质量升级”。Revision 11 发布后，普通人员对中文名称、模块、业务含义、用途和备注的维护继续走现有 Issue 事件协议。

## 4. Revision 11 数据流

1. 重新读取远程 `main`、Revision 10 和 manifest SHA；任一值变化立即中止，禁止覆盖并发更新。
2. 下载并验证 Revision 10 规范快照，作为唯一业务基线。
3. 将 Revision 10 快照写入隔离的临时 SQLite，不读取或上传本机连接配置表。
4. 基于发布者本机配置的 EOS 源码根目录和项目知识库根目录运行现有业务富化流程；公开制品不得记录这些绝对路径。
5. 应用本机已锁定人工覆盖；人工值优先于自动推断。
6. 将候选快照修订号设为 11，并执行结构、公开内容、路径、凭据特征和压缩回读验证。
7. 生成一次且只生成一次规范压缩载荷。
8. 同一字节数组同时写入：
   - `snapshot/latest.json.gz`
   - `snapshot/revisions/000000011-{sha256}.json.gz`
9. 写入 Revision 11 manifest 和管理员提升审计摘要。摘要只记录基线修订、基线哈希、新哈希、表数、字段数、实体数和生成时间，不记录本机路径。
10. 发布前再次核验远程 HEAD、Revision 和快照哈希；不一致则停止并重新生成。
11. 提交并推送 Revision 11 后，从远程重新下载快照，通过正式同步入口替换本机共享范围。
12. 核对本机共享 Payload SHA 与远程 manifest SHA 完全一致。

## 5. 远程文件与审计规则

Revision 11 提交只修改规范仓库中的下列公开文件：

- `snapshot/latest.json.gz`
- `snapshot/revisions/000000011-{sha256}.json.gz`
- `snapshot/manifest.json`
- `snapshot/promotions/000000011.json`
- `events/revisions/000000011.json`

`events/revisions/000000011.json` 的事件列表为空，表示该修订是管理员全量基线提升而不是普通字段事件。`snapshot/promotions/000000011.json` 提供完整的前后哈希和数量审计。manifest 的 `LastEventPath` 保留 Revision 10 的最后一条真实业务事件，避免伪造不存在的字段修改事件。

后续普通 Issue 成功处理时，从 Revision 11 增加到 Revision 12，继续使用现有不可变事件文件和快照修订规则。

## 6. “待生效 1”处理设计

### 6.1 本次清理

- 在 Issue #2 留下简短说明：该无效请求已被后续合法事件取代，当前规范值为“财务管理”。
- 关闭 Issue #2，停止每5分钟重复校验和重复评论。
- 将本机对应 OperationId `e2c0aaea371b48028e5eb545db90b682` 标记为终态 `Superseded`，不再计入待上传或待生效。

### 6.2 客户端永久修复

- 为本地操作状态增加终态 `Rejected` 和 `Superseded`。
- `LoadActivePendingOperations` 只返回 `Pending`、`Submitted` 和可重试 `Failed`。
- GitHub 客户端能够识别 `dictionary-event-invalid` 标签。
- 已被远程后续规范值取代的无效 Issue 标记为 `Superseded`；其他无效 Issue 标记为 `Rejected` 并保留错误原因。
- 两种终态都不计入“待生效”，但保留本机审计记录。
- 工作流对内容和更新时间未变化的无效 Issue 只评论一次，避免定时任务重复刷同一评论。

## 7. 实体映射与未来结构发布保护

- Revision 11 必须包含1,287个满足 EOS 源码实体证据规则的表。
- 主界面实体范围必须按稳定键返回同样的1,287张表。
- 结构维护重新扫描时，如果当前扫描暂时未产生实体映射，不得用空值覆盖上一规范快照中的高可信实体映射。
- 只有新的明确源码证据或人工锁定值可以替换原实体映射。
- 发布预览必须显示实体映射总数；从非零突然降为0时禁止确认发布。

## 8. 多人维护模型

普通维护人员不需要克隆数据仓库修改 JSON，也不需要数据库连接：

1. 获取相同版本的数据字典程序。
2. 配置具有目标仓库 Issues 读写和 Contents 读取权限的个人 GitHub Token。
3. 程序启动时自动拉取规范快照，此后每5分钟检查一次。
4. 人工保存表或字段业务信息后，客户端立即写本机 outbox 并提交 GitHub Issue。
5. GitHub Action 校验并生成下一规范修订。
6. 其他用户点击“更新字典”或等待定时同步即可取得新修订。

同一对象、字段和属性发生并发维护时，按成功处理的 Issue 编号顺序应用；最后成功事件成为当前值，每条事件仍保留审计记录。

只有 `config/publishers.json` 中登记的发布者允许执行结构扫描和管理员全量提升。普通维护人员不能修改数据库物理结构。

## 10. 失败与恢复

- 发布前保留本机 Revision 10 SQLite 备份和候选 Revision 11 快照备份。
- 远程写入采用单个 Git Commit；推送前远程 HEAD 变化则不提交任何远程内容。
- 推送后客户端回读失败时，不改写远程；修复客户端后重新下载同一 Revision 11。
- Revision 11 内容验证失败时，停止发布并继续保留 Revision 10 为规范版本。
- Git 历史、Revision 10 快照和全部既有事件保持不可变，可通过上一提交恢复 manifest 指向，但不删除 Revision 11 审计文件。
